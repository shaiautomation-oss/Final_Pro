## WF1 — אימות מסמכי מס
**קובץ:** `WF1 - Invoice Validation.json` · **טריגר:** Airtable, כל דקה · **Active**

| שלב | צומת | מה קורה |
|---|---|---|
| 1 | `חשבונית חדשה` | סורק את `Invoices` כל דקה לפי השדה `Created` |
| 2 | `המתנה לסיום ההקלדה` | ממתין 90 שניות |
| 3 | `קריאת החשבונית מחדש` | קורא את הרשומה מ-Airtable עם הנתונים העדכניים |
| 4 | `בדיקת תקינות` | `Amount > 0` **וגם** `CustomerId` אינו ריק |
| 5 | `קריאת כל החשבוניות` | קורא את כל החשבוניות הקיימות |
| 6 | `ספירת חשבוניות` | Summarize — סופר אותן |
| 7 | `חישוב מעמ ומספר מסמך` | Edit Fields — מע"מ, סכום כולל, מספר מסמך רץ |
| 8 | `עדכון והכנסה לתור` | כותב חזרה ומסמן `Status = Ready` |
| 9א | `סימון כפסולה` | ענף "לא" — `Status = Invalid` |
| 9ב | `פתיחת משימת תיקון` | פותח משימה ב-`Tasks` |

**המסלול:** שלב 4 מתפצל — ענף "כן" ממשיך ל-5→6→7→8, ענף "לא" הולך ל-9א→9ב.

### למה יש המתנה בשלב 2

ב-Airtable הרשומה **נוצרת ברגע הלחיצה על `+`** — לפני שהמשתמש הספיק להקליד סכום
ולקוח. הטריגר מקבל תצלום של הרשומה מרגע היצירה, ולכן בלי ההמתנה כל חשבונית
שמוקלדת ידנית הייתה מסומנת `Invalid` תוך שנייה.

ההמתנה של 90 שניות נותנת זמן להקלדה, ואז `קריאת החשבונית מחדש` שולף את הנתונים
העדכניים מ-Airtable. **הצמתים שאחריו קוראים מהשליפה הטרייה ולא מהטריגר** —
זה מה שהופך את התהליך לאמין.

חשבונית שנוצרת דרך האפליקציה (WF13) מגיעה מלאה מלכתחילה, וההמתנה רק מעכבת
אותה ב-90 שניות.

**חישוב המע"מ** יושב בצומת `חישוב מעמ ומספר מסמך`:
```
שיעור     = Created >= 01/01/2025  ?  0.18  :  0.17
VatAmount = עיגול(Amount × שיעור, 2 ספרות)
Total     = עיגול(Amount + VatAmount, 2 ספרות)
```

**מספור רץ:** `INV-<שנה>-<מונה בן 4 ספרות>`, המונה = מספר החשבוניות + 1.
זו נקודת החולשה הידועה: שתי חשבוניות שנוצרות באותה דקה יקבלו אותו מספר.


## WF13 — Webhook לאפליקציה
**קובץ:** `WF13 - App Webhook.json` · **טריגר:** POST מ-Base44 · **Active**

| שלב | צומת | מה קורה |
|---|---|---|
| 1 | `בקשה מהאפליקציה` | Webhook — מקבל `{ action, table, payload }` |
| 2 | `ניתוב לפי פעולה` | Switch על `action` |
| 3א | `סוכן האפליקציה` | ענף `chat` — AI Agent עם שני כלי RAG |
| 4א | `תשובה - שיחה` | מחזיר `{ ok, reply }` |
| 3ב | `קריאת רשומות` | ענף `list` |
| 4ב | `תשובה - רשימה` | מחזיר `{ ok, table, records }` |
| 3ג | `הכנת רשומה חדשה` | ענף `create` — פורש את `payload` |
| 3ד | `יצירת רשומה` | Airtable create |
| 4ג | `תשובה - נוצר` | מחזיר את הרשומה |
| 3ה | `הכנת עדכון` | ענף `update` — `payload` חייב לכלול `id` |
| 3ו | `עדכון רשומה` | Airtable update |
| 4ד | `תשובה - עודכן` | מחזיר את הרשומה |
| 4ה | `תשובה - פעולה לא מוכרת` | כל `action` אחר — HTTP 400 |

**תת-צמתים של הסוכן:** `מודל שפה` · `זיכרון שיחה` · `policies - מדיניות` ·
`products - מוצרים` · `המרה לווקטורים`.

זו **נקודת הכניסה היחידה** של האפליקציה למערכת. מפתח ה-Airtable יושב רק
כאן, ב-Credential של n8n — האפליקציה לא מכירה אותו בכלל.

| action | גוף הבקשה | תשובה |
|---|---|---|
| `chat` | `{ action, message, sessionId? }` | `{ ok, reply }` |
| `list` | `{ action, table, limit? }` | `{ ok, table, records }` |
| `create` | `{ action, table, payload }` | `{ ok, action, record }` |
| `update` | `{ action, table, payload }` — `payload` חייב לכלול `id` | `{ ok, action, record }` |

שמות טבלה מותרים: `Invoices` · `Leads` · `Products` · `Tasks`.
שם הטבלה מתורגם למזהה בתוך ביטוי בצומת Airtable, כך שהאפליקציה שולחת שם
קריא ולא מזהה פנימי.

**דוגמאות:**
```json
{ "action": "list", "table": "Invoices", "limit": 50 }
{ "action": "create", "table": "Leads",
  "payload": { "Name": "דנה לוי", "Email": "dana@example.co.il",
               "Company": "לוי טכנולוגיות", "Status": "New" } }
{ "action": "update", "table": "Invoices",
  "payload": { "id": "recXXXX", "Status": "Paid" } }
{ "action": "chat", "message": "כמה חשבוניות פתוחות יש לי?" }
```
